# DeepSeek-first Harness Engineering：三个开源项目的源码审计笔记

> Working Paper · 2026-05-18  
> 一手来源：Hmbown/DeepSeek-TUI、esengine/DeepSeek-Reasonix、antirez/ds4 的 README、docs、源码与本地 CLI 审计结果  
> 附属于附件一的生态观察补充  
> 注：本文是开源项目调研笔记。核心结论经 README/docs/source audit 校准；star 数、热度榜单和社区传闻不作为论证依据。

---

这篇文章看三个 DeepSeek 生态相关开源项目：DeepSeek-TUI、Reasonix、ds4。它们不在同一个工程层：

- **DeepSeek-TUI**：应用层，一个 Rust 终端 coding agent；
- **Reasonix**：agent loop 层，一个 DeepSeek-native coding agent / agent-loop library；
- **ds4**：推理层，一个 DeepSeek V4 Flash 专用本地推理引擎。

我最初把三者概括为 single-model commitment，源码审计后需要修正：这个概念只完整适用于 ds4，基本适用于 Reasonix 的产品立场，但不适用于 DeepSeek-TUI。DeepSeek-TUI 明确支持 10 个 provider，是 multi-provider architecture；Reasonix 官方立场是 DeepSeek-only on purpose，但源码里保留了 `ModelClient` port，存在未来 pluggable 的结构性余地；ds4 才是真正的单模型专用路径。

更稳的概括是：**DeepSeek-first harness engineering**。三者共同点不是都绑定单一 backend，而是都在不同层面对 DeepSeek 的模型行为、API 形态、prefix cache、tool calling 与生态入口做了有方向的工程适配。它们揭示的不是“所有 harness 都应该 single-model”，而是：当模型、API、推理与产品层能围绕同一组行为假设协同时，harness 的设计空间会明显不同。

## 一、DeepSeek-TUI：应用层的结构化控制面

DeepSeek-TUI 的 README 第一行就是它的定位：Terminal coding agent for DeepSeek V4。源码审计确认，它是一个 Rust edition 2024 的多 crate workspace，包含 `deepseek` dispatcher CLI 与 `deepseek-tui` TUI runtime。TUI 之下是 async engine，模型调用走 OpenAI-compatible streaming client。

它不是 single-model commitment。`ApiProvider` enum 支持 Deepseek、DeepseekCN、NvidiaNim、OpenAI、Atlascloud、OpenRouter、Novita、Fireworks、SGLang、vLLM、Ollama 等 provider。这个事实很重要：DeepSeek-TUI 的产品姿态是 DeepSeek-first，但架构上是 multi-provider。

这反而更能说明它的产品取舍。DeepSeek-TUI 不是在推理层压榨一个模型，而是在应用层做几件更像产品基础设施的事：

1. **模式结构化**：Plan / Agent / YOLO 三种模式在 docs 与 engine loop 中都有明确状态。Plan read-only，Agent 交互审批，YOLO 自动批准。这里的核心不是“三个按钮”，而是把 agent 行为边界显式化。

2. **Auto mode**：`auto_router.rs` 与 `auto_reasoning.rs` 支持每 turn 选择 model 与 thinking effort。它先用一个 flash routing call 判断本轮任务该用什么模型和推理强度。这个设计体现的是成本治理：用户不该每次手动决定“该不该上更贵模型”，harness 可以把选择做成 runtime policy。

3. **状态持久化**：`session_manager.rs` 把 session 序列化到 `~/.deepseek/sessions/`，有 schema version、会话数上限和消息数上限；`task_manager.rs` 支持 durable task queue，running task 在重启后可 re-queue；workspace rollback 用 side-git repo 存快照，不碰用户自己的 `.git`。这不是 cache 优化，而是 session continuity。

4. **系统级约束替代用户疲劳**：源码审计显示 sandbox 需要精确表述：macOS Seatbelt 实现完整；Linux Landlock 有 syscall 实现，但 subprocess sandboxing 仍有 helper binary 缺口；Windows Job Objects 目前是 stub，不应宣传成可用。即便如此，方向很清楚：把保护从“用户每次会判断”下沉到 OS 或 runtime 能力边界。

5. **LSP diagnostics 进入 edit lifecycle**：`lsp_hooks.rs` 在 `edit_file`、`write_file`、`apply_patch` 后运行 diagnostics，并在下一次 API 请求前把结果作为 synthetic user message 注入。它不是等模型之后自己发现错误，而是把验证器接进 harness 主循环。

6. **sub-agent 用 structured event 回传**：`<deepseek:subagent.done>{JSON}</deepseek:subagent.done>` 是源码里的真实 sentinel，配合 mailbox lifecycle events。这个设计把“子任务结束后 parent 必须合成”变成协议层约束。

7. **skills 兼容已有生态资产**：源码审计发现它会从 8 个路径发现 skill，包括 `.opencode/skills`、`.claude/skills`、`.cursor/skills`、global skills 与 native paths，还支持 GitHub repo / URL / curated registry 安装，并做 path traversal、symlink、size cap 等安全处理。这一点比单纯“有 skills 系统”更重要：后发者不要求用户重写已有资产，而是迁就既有格式。

DeepSeek-TUI 对我最有价值的观察，不是它有多少功能，而是它在应用层把很多本来依赖模型自觉或用户判断的环节做成系统约束：mode、approval、LSP、snapshot、session、sub-agent event、skill discovery。它走的是“提前结构化”的路线：control plane 前移，运行时只在被结构化过的边界里活动。

## 二、Reasonix：cache-aware agent loop

Reasonix 的定位需要比“agent loop framework”更精确。README 称它是 DeepSeek-native AI coding agent for your terminal；源码同时导出 `CacheFirstLoop`、`ImmutablePrefix`、`AppendOnlyLog`、`VolatileScratch` 等 library entry。更稳的说法是：**一个以 DeepSeek-first coding agent 为产品面的 agent-loop library**。

Reasonix 的核心设计不是多 provider 兼容，而是 cache-first。README 中有一句原话：DeepSeek-only on purpose. Coupling to one backend is the feature, not a limitation. 但源码也保留了 `ModelClient` port，architecture doc 说明 OpenAI-compatible shim 理论上可通过 `--model` override 工作，只是未经测试、不作为目标。这说明它是 DeepSeek-only by design，而不是技术上永远无法抽象。

源码审计确认，Reasonix 的三层 context 分区是真实结构，不只是文档比喻：

- `ImmutablePrefix`：system prompt、tool specs、few-shots；
- `AppendOnlyLog`：消息与工具结果单调追加，只有 compact 是例外路径；
- `VolatileScratch`：每 turn reset 的 reasoning / planState / notes。

这个分区不是按“内容类型”分，而是按“会不会破 prefix cache”分。DeepSeek API 的 prefix cache 要求前缀稳定，因此 Reasonix 让稳定内容进入 immutable prefix，让对话进入 append-only log，把短期波动隔离到 scratch。这里的 cache 是 API 层的 server-side prefix cache，不是本地 KV cache。

Reasonix 的 tool-call repair pipeline 也经审计确认：`flatten.ts`、`scavenge.ts`、`truncation.ts`、`storm.ts` 都是真实源码模块。需要修正的是运行顺序：flatten 在 tool registration 阶段处理 schema；per-turn order 是 scavenge -> truncation -> storm。这不是通用错误恢复，而是围绕 DeepSeek tool-calling failure modes 做的专门补偿。

Reasonix 还有第三个容易被忽略的 pillar：cost control。它不只是 cache-first + repair，还包括 flash-first 默认、turn-end auto-compaction、`/pro` 单 turn 提权、failure-signal auto-escalation 等策略。也就是说，它把“省钱”不是当 UI 上的账单统计，而是做进 agent loop 的调度策略里。

99.82% cache hit 这个数字可以引用，但必须降级为社区 case study，而不是 repo 自己的 benchmark。`benchmarks/real-world-cache/README.md` 记录的是一个真实用户在 2026-05-01 的 DeepSeek dashboard：约 435M input tokens，99.82% cache hit，花费约 $12.34；$60.63 是同一 workload 在 0% cache hit 下的反事实估算，不是一个“通用 framework 实测成本”。这仍然很有价值，但应该说清楚它是 community case study shared with permission。

两个新观察值得保留：

1. **ACP support**：`src/acp/` 与 CLI subcommand 说明 Reasonix 不只是一个 TUI/CLI agent，还尝试进入 Agent Client Protocol 生态。这让它有机会成为多 agent orchestration 的参与者。

2. **parallel tool dispatch with safety guarantees**：tools 标记 `parallelSafe`，dispatcher 可以并发执行安全工具，但按声明顺序 yield results。这是一个很 harness 的判断：并行不是让模型“自己协调”，而是通过工具元数据和 dispatcher policy 保证语义顺序。

Reasonix 的产品品味在于：它没有把“兼容所有模型”当默认美德，而是承认 DeepSeek prefix-cache mechanic 是一个可以被工程化利用的约束面。它的价值不在于抽象得最通用，而在于把某个 backend 的具体行为利用到足够深。

## 三、ds4：推理层的模型专用优化

ds4 是三个项目中 single-model commitment 最彻底的一个。README 明确说：DwarfStar 4 is a small native inference engine specific for DeepSeek V4 Flash；not a generic GGUF runner, not a wrapper around another runtime；completely self-contained。Makefile 也没有链接 GGML runtime，虽然项目明确承认受 llama.cpp / GGML 启发，并保留相关 MIT license attribution。

ds4 对 harness 的意义在于：它把 agent 场景里的 cache 稳定性推到推理层。

第一，**KV cache 是磁盘一等公民**。README 和 `ds4_server.c` 都明确记录了 on-disk KV persistence。源码里有手写 SHA1 实现，按 rendered text bytes 生成 key，`.kv` 文件由 40 位 SHA1 hex 命名。`kv_cache_find_text_prefix()` 会遍历 cache 目录匹配前缀。这里不再是“API 层尽量让 prefix 稳定”，而是推理引擎自己持久化 KV state。

第二，**tool call replay 到 byte level**。ds4 会记录模型当时采样出的 exact DSML block，存到 `raw_dsml`，下一次 replay 如果 tool id 可匹配，就原样复用 raw block，而不是重新按 JSON 语义渲染。只有当 tool id 未知或功能关闭时，才回退到 canonical JSON-to-DSML rendering。这个设计直指 agent 场景的 cache killer：语义相同不等于 token 序列相同，byte-level 稳定才保护 KV cache。

第三，**协议兼容服务于生态进入**。ds4 同时支持 OpenAI `/v1/chat/completions`、OpenAI `/v1/responses`、Anthropic `/v1/messages`，另有 `/v1/completions`。这不是为了做协议创新，而是为了让 Codex / Claude Code / OpenAI-compatible clients 都能接入本地 DeepSeek V4 Flash。Protocol 是 commodity，optimization 是 differentiation。

第四，**不对称量化要精确表述**。原先说 shared experts / projections / routing layer “保持原精度”不准确。源码审计显示，published GGUF 中非 routed components 多为 Q8_0 / 8-bit，高于 routed MoE experts 的 aggressive 2-bit，但不是完全原精度。更准确的说法是：只有 routed MoE expert tensors 使用 2-bit asymmetric quantization（gate/up: IQ2_XXS，down: Q2_K）；非 routed components 使用更高精度（如 Q8_0）以保护质量。

第五，**benchmark 不能过度外推**。README 中 M3 Max 数字对应 MacBook Pro M3 Max, 128 GB，而不是 96 GB；且是 single-run Metal CLI numbers，不是可复现实验集。它可以说明方向，但不该承担结论重量。

ds4 还有一个值得写进投递材料的细节：README 明确说项目使用 GPT 5.5 强辅助，但 humans lead the ideas, testing, and debugging。这个透明度很适合当前岗位语境：AI-assisted engineering 的关键不是遮掩 LLM 参与，而是人类是否保留问题选择、架构判断、测试与最终责任。

## 四、三层之间真正共享了什么

源码审计后，三者的共同点不是“都 single-model commitment”，也不是“都在做 cache”。更准确地说：

- DeepSeek-TUI 做的是 **application state continuity**：session、task、snapshot、mode、approval、LSP、sub-agent event；
- Reasonix 做的是 **API-layer cache-aware loop**：prefix partition、append-only log、volatile scratch、tool-call repair、cost control；
- ds4 做的是 **inference-layer cache persistence**：SHA1-keyed `.kv`、exact DSML replay、protocol-compatible local serving。

所以 cache 这条线只在 Reasonix 和 ds4 上真正贯通。DeepSeek-TUI 的 session save/resume 不是 cache 优化，不应被硬塞进 cache narrative。它的价值在另一侧：把用户使用 agent 所需的状态、权限、恢复、验证和生态资产管理起来。

三者合在一起，反而给出更完整的 harness 图景：

1. **应用层要关心用户能不能长期、安全、可恢复地工作。**
2. **agent loop 层要关心前缀是否稳定、工具输出是否可修复、成本曲线是否可控。**
3. **推理层要关心 KV cache 是否能跨 session 复用、tool-call bytes 是否稳定、协议是否能兼容已有 agent。**

这就是 DeepSeek-first harness engineering 的含义：不是把 DeepSeek 当一个 OpenAI-compatible endpoint 换进去，而是在不同层面利用、暴露、保护和放大 DeepSeek 相关的模型与推理行为。

## 五、后发者的生态策略

三个项目里还有一条产品策略线：后发者不要求用户重写工作流。

DeepSeek-TUI 自动发现 Claude Code、Cursor、OpenCode 等既有 skill paths；ds4 同时暴露 OpenAI 与 Anthropic 风格协议；Reasonix 以 CLI 为 canonical surface，同时尝试 desktop prerelease、ACP、QQ channel 与中英双语界面。这些动作不是单纯“兼容性功能”，而是生态进入策略：用户已有资产越多，新工具越应该迁就既有格式。

这条策略有窗口期。生态格式还没完全碎片化时，后发者可以通过兼容既有 assets / protocols 降低迁移成本；一旦格式固化到互不兼容，进入成本会快速上升。

## 六、结论

既有 Claude Code / Codex 二分，主要比较的是 runtime 可变性放在哪里：Claude Code 更像现场运行时，Codex 更像设计时控制面。DeepSeek 生态这三个项目提示了另一个正交维度：**对 backend 行为做多强假设**。

DeepSeek-TUI 在应用层走的是 multi-provider 但 DeepSeek-first 的产品路线；Reasonix 在 agent loop 层把 DeepSeek prefix-cache behavior 作为设计约束；ds4 在推理层彻底绑定 DeepSeek V4 Flash，把 KV cache 和 DSML replay 做进本地引擎。

这不是同一条路线的三个复制品，而是一个生态在三个层级上的不同试验。对 Harness PM 来说，真正值得学习的是它们如何把模型行为、用户状态、工具权限、cache 经济性和生态迁移成本翻译成产品结构。这个能力，比“支持几个 provider”或“有多少功能”更接近 harness 的核心。
