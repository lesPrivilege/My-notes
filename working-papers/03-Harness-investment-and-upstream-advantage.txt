# 外化天花板与上游下场：Harness 投资的结构性不对称

> Working Paper · 2026-05-18

---

Harness 工程有一个不太舒服的事实：它的生命周期不只由工程质量决定，还由底层模型的进步速度决定。

每次模型升级，harness 中相当一部分外部补丁都需要被重新标定：有些 prompt 约束会变成冗余，有些 fallback 会被模型内化，有些原本有效的 repair 规则会因为新模型的行为分布变化而变得有害。这不是「技能会过时」这种普通折旧。技能赖以存在的对象本身每轮都在被替换。更准确地说，每个 harness 组件都是对特定模型、特定 effort level、特定任务分布下某个具体失败模式的补偿——三个维度任一变化，补偿逻辑就可能从有用变成无用甚至有害。

把这个观察推广：当前 AI 工程中所有不修改模型权重的改进——prompt engineering、harness 框架、managed agents、alignment monitoring——本质都是同一件事：externalization。在不改变模型权重的前提下重组外部运行时环境。这类改进的天花板不来自工程努力不足，来自模型底层表征的几何结构——后者由训练目标雕刻，不为使用需求服务。

这是前提。下面要讨论的是：贬值是真实的，但贬值的承受方不同。

---

## 一、贬值逻辑的两面

Anthropic 说 harness 应该变薄。小米说 harness 应该变厚。两边都对，但不对称。

Anthropic 站在模型前沿，看到的是 harness 的递减价值。小米站在追赶期，看到的是 harness 的当下杠杆。变厚策略有一个内在矛盾：你投入越多资源在框架上，模型进步越快让这些投入贬值。变薄策略没有这个矛盾，因此是收敛方向。[^1]

但「变薄是收敛方向」对追赶者不可操作——你不能在模型能力不足时拆掉脚手架。所以真正的问题不是「变薄还是变厚」，而是「谁在做 harness，决定了 harness 的贬值去向」。

下游做 harness，贬值是净损失：模型一更新，之前的适配工作部分作废，团队要重新标定。Reasonix 用逆向工程把 cache hit 推到 99.82%，是社区在外部观察下的最优解——但 DeepSeek 模型 API 行为一变，它的 4-pass tool-call repair pipeline 可能需要全部重调。[^2]

上游做 harness，贬值是信号：哪些组件被拆掉，标记了模型已经内化的能力；哪些还在，标记了仍需外部补偿的缺陷。持续删减、重写、回归测试 system prompt 和 harness 规则，本质上是在绘制模型能力的等高线。[^3] 这种诊断价值下游拿不到——下游只能读到公开版本，看不到内部演进历史，也不拥有模型权重和训练环境来验证「这个补丁到底在补什么」。

更直接地说：上游的 harness 使用数据本身就是模型改进的结构化输入。tool call 执行后被用户回滚、agent 决策触发了用户显式干预、模型能力不足被 harness 层拦截——对下游，这些是运营成本；对上游，是训练信号。

## 二、上游碾压不是单点优势

外部 harness 公司的整个能力空间很大程度上是上游能力空间的子集。生态繁荣不一定等于护城河，也可能只是厂商路线图还没覆盖到那个区域的窗口期。当模型提供方把某类工作流做成官方参考实现、SDK 或托管运行时，下游方案商往往会从「定义架构」退到「做定制配置」。[^4]

这个碾压路径不是靠一个产品完成的。它包括标准定义权（Google Skills Repository + MCP 协议）、开发者工具链控制（ADK + agents-cli）、运行时基础设施（Agent Runtime、fleet orchestration）。下游的生存空间不是被一个产品打掉的，是被整个基础设施栈逐层挤压的。[^5]

官方 demo 或参考实现的杀伤力不在技术复杂度，而在参照系定义权。参考实现一旦被市场接受，下游方案商从卖架构设计降级为卖定制配置。SDK 绑定把开发者锁进生态。Demo 是教育市场的外衣，生态锁定才是目的。[^6]

还有一个更微妙的效应。同一段 prompt 文本，在个人私部署架构里接近无用，在官方 orchestration + grounding + 精细控件的架构里产生断层级效果。不是 prompt 在贬值，是外化层的效力在沿架构边界重新分配——而且方向是确定的：往模型提供方集中。[^7]

这些加在一起的含义是：模型层的领先不自动转化为生态控制力。一个模型提供方如果只有 API 一个触达开发者的界面，标准定义权、开发者工具链、运行时基础设施这三个杠杆就全部握在已有 harness 产品的厂商手里——不管模型本身的性能多强。模型层的优势通过 API 定价只能间接变现，而 harness 层的控制力可以直接建立开发者和终端用户的粘性。这是行业结构决定的，不是单个公司的策略选择问题。

## 三、Cache 作为跨层设计原理

贬值讨论的一个容易被忽略的侧面：不是所有 harness 都同等贬值。有一类 harness 设计锚定在物理约束上而非模型行为上，它的生命周期和模型版本无关。

一个观察：从 over-training 把高频 pattern 烧进权重，到 MoE 稀疏激活只调动相关 expert，到 KV cache 命中避免重复 prefill，到 system prompt caching 最大化前缀复用——四个抽象层，做的是同一件事：把重复计算前置，运行时只处理增量。不是巧合。Memory bandwidth 是硬瓶颈，所有层的优化方向被它统一了。[^8]

这个统一原理在 DeepSeek 生态中有三层实施：

模型层——CSA/HCA 混合注意力，百万上下文 KV cache 压到 V3.2 的 10%，FLOPs 压到 27%。FP4 量化感知训练不是部署时量化，训练阶段就让模型适应 FP4。[^9]

推理层——ds4（antirez）把 KV cache 当磁盘一等公民。KV checkpoint 以 SHA1 为 key 写入 .kv 文件，exact 前缀跨 session 甚至跨服务器重启复用。DSML tool-call replay 确保 agent 场景下 tool call 返回结果不破坏前缀一致性。Cache 的生命周期从 per session 拉长到 per deployment。[^10]

框架层——Reasonix 的三段式 context 分区（IMMUTABLE PREFIX / APPEND-ONLY LOG / VOLATILE SCRATCH），99.82% cache hit rate。它为什么能做到？因为它只绑定 DeepSeek 一个后端——coupling to one backend is the feature, not a limitation。[^11]

三层放在一起看：cache 优化不再是「框架层想办法少浪费 token」，而是从模型 API 设计、到推理引擎实现、到框架 architecture，共享同一套 cache 契约。

这件事第三方做不了。第三方不控制推理引擎，也不定义 API 的 cache 行为。它最多在框架层做 prompt engineering 来补偿 cache miss——本质上是用补丁补偿另一层补丁。而上游可以让模型的 tool calling 行为本身就与 harness 的 schema 对齐，不需要 Reasonix 那样的 4-pass repair pipeline。

这类围绕物理约束（而非模型行为特征）的 harness 设计，贬值速率低得多。Memory bandwidth 不会因为模型更新而改变。

## 四、Coding agent 的商业逻辑与飞轮条件

为什么 coding agent 的 harness 生态成熟远快于法律、医疗？不是「发展更快」，是三个前提条件同时满足：可分解的中间表示（代码可局部编辑）、廉价的自动验证（编译器 / 测试套件）、错误可逆且代价低。[^12]

三条件放在一起构成飞轮：context 采集层（git history、AST、依赖图）+ 微调信号层（issue → PR 的天然三元组）+ 验证闭环层（测试套件 + type checker）。每层都有现成的成熟方案，飞轮自转。[^13]

其他领域呢？法律文书有可分解的中间表示，但缺廉价验证和低代价错误恢复。视频生成端到端概率生成压掉了中间表示层，前两条都缺。三条件是必要不充分的——古籍校勘三条件皆具（异文是结构化中间表示，音韵通假规则可形式化验证，校勘记天然容错），却因跨域人才极少、数据格式不兼容而停滞。隐含的第四条件：必须有足够密度的人同时站在技术与领域的交叉点上。[^12]

在验证器缺位的领域，会发生一件事：用户能碰的界面只剩 prompt 一个旋钮。prompt 模板市场、「教你写出高质量提示词」的教程——本质是用经验规则近似替代反馈回路。这些规则拟合的是当前模型版本的行为，模型一更新就废了。[^14]

Coding 不一样。编译器说你错了就是错了。Coding harness 的一部分价值锚定在模型外部的确定性检验器上，不完全随模型行为漂移。

但有一个容易被忽略的问题：agent 加速产出的同时也在加速代码库的熵增。agent 每多跑一步，代码库就多一份被修改的概率。agent 输出速度和人的 review 能力之间出现了速度差。[^15] 这意味着有些 harness 不是补偿模型缺陷，而是补偿 agent 加速带来的新问题——这类 harness 的生命周期可能与 model 进步正相关而非负相关：模型越强、agent 越快，entropy 累积越快，工程纪律类的 harness 反而越重要。

渗透率预期也值得提一句。当前市场定价隐含的假设是 AI 均匀渗透各行业。实际不是。Coding 接近范式替换，大部分其他领域还停在「高级搜索引擎」阶段。这个预期错配比估值数字本身更值得关注。[^16]

## 五、Harness 的非贬值价值

前面四节论证了 harness 的技术补丁价值确实会贬值，但贬值是不均匀的，且承受方不同。这一节讨论 harness 中哪些维度的价值不随模型版本更新而消失。

合规与治理（audit trail、policy enforcement）——制度需求，不因模型变强而消失。可观测性（logging、tracing、failure mode taxonomy）——运行时基础设施需要独立于模型能力。多模型编排——当底层模型频繁切换时，统一接口层的价值反而上升。诊断记录——哪些 harness 被拆了、哪些还在，这个历史本身就是信号。[^17]

还有一类容易被忽略的：弱模型不知道自己到了能力边界。这不是 harness 能解决的问题——是模型 calibration 的内部问题。但 harness 层能成为探测系统：观测模型在哪些任务上频繁拒绝、哪些沉默失败、哪些反复尝试仍失败。这些信号不告诉研究团队「怎么修」，但能告诉「哪里需要修」。[^18]

Pro 在 agentic fetch 任务中表现比 Flash 更差。不是因为能力不足，是推理预算更高让它在死胡同里「想得更多」而非「更早放弃」。推理能力变强，元认知判断没变强。知道什么时候该停，是一个独立维度。[^19] 这意味着 harness 层不能信任模型自己判断「什么时候该停」，需要外部止损机制——超时、结果验证、多路径并行后择优。

这三层——可观测性基础设施、止损机制、把前两层输出翻译成对模型能力边界的判断——构成了 harness 的非贬值核心。它不是补丁，是模型进化的诊断系统。

## 六、结论：上游做 Harness 是位置问题

外化天花板对下游是天花板，对上游是可调节的遮阳板。

下游做 harness，投的是一笔会被模型进步持续折旧的资产。上游做 harness，折旧的同时获得三笔下游拿不到的收益：训练信号（harness 失败模式回灌）、能力等高线（负空间地图的持续绘制）、跨层 cache 契约（物理约束锚定的设计不折旧）。

「只做引擎不做车」的策略在模型追赶期是有效的——资源集中在核心能力上，回报最高。但模型层一旦进入领先位置，这套策略的内在矛盾就浮现了：没有自己的 harness 层，模型进化的诊断信号只能从第三方 API 使用数据中间接推断，标准定义权和开发者粘性留在做 harness 的厂商手里。从「只做引擎」到「同时做车」，不一定是背离原策略——引擎造到一定程度，需要一个场景来验证极限性能、同时收集引擎哪里该改进的结构化反馈。

变薄是收敛方向。但收敛的主语是上游。
