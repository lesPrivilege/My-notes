# Agent 范式第一性原理

> 7 条根原理覆盖 Agent 系统的核心概念。按原理组织，不按题目顺序。

---

## 原理索引

| # | 原理 | 一句话 |
|---|------|--------|
| P1 | LLM 是概率预测器 | 无状态、无记忆、可能幻觉——一切都源于「预测下一个 token」 |
| P2 | Context window 是唯一工作内存 | 每个 token 都要挣位置；窗口外的信息等于不存在 |

## P1：LLM 本质是概率性的下一 token 预测器

LLM 的全部行为——从生成流畅文本到产生幻觉——都源于它是一个「给定前文预测下一个 token 的概率分布」。它没有状态、没有记忆、没有对世界的直接感知。

**第一性推导**：

1. LLM 做的事只有一个：给定 token 序列 [t1, t2, ..., tn]，输出 P(tn+1 | t1..tn) 的概率分布，采样得到下一个 token。
2. 因为是概率采样，同一个输入可以产生不同输出（temperature > 0 时）。这不是 bug，是设计。
3. 因为只预测下一个 token，它没有「全局规划」能力。所以 CoT 有效，因为推理过程本身成了后续 token 的上下文。
4. 因为训练数据有截止日期且是统计规律而非事实数据库，它会「自信地编造」——这就是幻觉。
5. 因为无状态，每次调用都是独立的。跨会话记忆、工具调用结果——全部需要外部系统注入到 context window 中。
6. 因为 Transformer 架构，所有 token 的关系通过自注意力机制计算。

**由此可推**：

- Agent vs LLM 区别：LLM 只预测 token，Agent 在外面加了循环+工具+记忆+目标
- 为什么需要 RAG/记忆/工具：LLM 无状态无外部知识，必须从外部注入
- 幻觉成因与缓解：概率模型生成「统计合理」而非「事实正确」的 token；缓解靠检索约束+引用溯源

## P2：Context window 是有限且唯一的「工作内存」

Context window 是 LLM 唯一的「工作内存」——所有它能「看到」并据此生成的信息，必须在这个窗口里。

**第一性推导**：

1. LLM 只能基于 context window 内的 token 生成。超出的部分直接被截断。
2. 你要 LLM 回答私有知识库的问题，就必须把相关文档塞进窗口——这就是 RAG 的本质。
3. 窗口有限（128K token ≈ 一本小书），所以必须选择塞什么。选择的质量决定了 LLM 的输出质量。
4. Lost in the Middle：LLM 对窗口中间位置的信息关注度最低，对开头和结尾最高。
5. 上下文工程的 4 种操作：Write（往窗口写什么）、Select（选哪些信息加载）、Compress（怎么压缩）、Isolate（隔离不同任务的上下文）。

**由此可推**：

- RAG vs Fine-tuning：RAG 往窗口注入外部知识（可更新），微调改模型权重（不可逆）
- 完整 RAG 流水线：清洗→分块→embedding→向量库→检索→rerank→注入 context→生成
- 有了超长上下文还需要 RAG 吗：需要——成本、延迟、检索精度、更新频率都是 RAG 的优势

## P3：Agent = LLM + 循环 + 工具 + 目标

Agent 和 Workflow 的分水岭只有一个：**控制权在谁手里**。Workflow 的控制权在代码，Agent 的控制权在 LLM。

**第一性推导**：

1. LLM 只会预测下一个 token（P1）。要让它「做事」，需要给它工具（P4）和循环——每次 LLM 输出一个决定，系统执行后把结果喂回 LLM，LLM 再决定下一步。
2. 控制权在 LLM 意味着：同一个 Agent 面对不同输入，可能走完全不同的路径。这是灵活性的来源，也是不可预测性的来源。
3. ReAct 是最基础的 Agent 范式：Thought→Action→Observation 循环。透明可审计，但 Token 消耗大。
4. Plan-and-Execute 优化 Token：先让 Planner 生成完整计划，再让 Executor 逐步执行。消耗约 ReAct 的 20%。
5. Reflection 提升质量：生成→评估→修改→循环，直到达标。

**由此可推**：

- Workflow vs Agent：控制权在代码 vs LLM；Token 消耗 1x vs 4-8x；可预测 vs 灵活
- 什么时候用 Agent：确实需要自主决策才上；能用 Workflow 解决就别用 Agent
- Multi-Agent 设计：Anthropic 警告——一个强大的单 Agent 比多个简单 Agent 更稳定更省钱

## P4：工具调用 = 结构化输出 + 由你的代码执行

LLM 自己不执行任何函数。它只输出「我想调用什么函数、传什么参数」的结构化指令，由你的应用程序实际执行。

**第一性推导**：

1. LLM 只能生成文本（P1）。要让它「做事」，需要一种方式让它表达「我想调什么函数」——这就是 Function Calling。
2. 关键认知：LLM 不执行函数。它只输出指令，真正执行的是你的代码。这个设计保证了安全性。
3. MCP 解决 N×M 爆炸：没有 MCP 时，N 个应用 × M 个工具 = N×M 套集成代码。MCP 变成 N+M。

**由此可推**：

- Function Calling 原理：LLM 输出结构化 JSON 调用指令，代码执行后结果回传
- MCP 解决什么：N×M → N+M，工具接入标准化
- 工具幻觉：LLM 调用不存在的工具；解法：严格校验工具名

## P5：输出不确定 → 必须外部校验

因为 LLM 输出是概率性的（P1），你永远不能 100% 信任它的输出。必须在 LLM 外面建校验层。

**第一性推导**：

1. LLM 输出不确定 → 同一个输入可能产生不同输出 → 不能假设输出总是对的。
2. 所以需要 guardrails：输入层（拦截 Prompt Injection）、输出层（检查幻觉/敏感信息）、工具层（拦截危险操作）。
3. 高风险操作必须 HITL：删除数据、发送邮件、资金操作——暂停执行，等人工确认。
4. 评估不是一次性的：上线前要评估（离线指标），上线后要监控（线上漂移）。
5. 可观测性是区分度：区分「会调 API」和「会做可靠 Agent」的分水岭。

**由此可推**：

- Agent 安全可控：最小权限 + HITL + guardrails 三层
- Prompt Injection 防御：数据/指令分离 + 输入过滤 + 上下文标记
- LLM-as-Judge：用 LLM 评估 LLM 输出；成本低但有偏见

## P6：成本与延迟 ≈ 循环步数 × 模型大小 × context 体积

Agent 系统的成本和延迟由三个因子的乘积决定。优化任何一因子都有 trade-off。

**第一性推导**：

1. Agent 循环一次 = 一次 LLM 调用。Plan-and-Execute 的 Token 消耗约 ReAct 的 20%。
2. 模型大小直接决定单次调用成本。简单子任务用小模型，复杂推理用大模型——这就是模型路由。
3. Context 体积影响输入 token 数（直接计费）和注意力计算复杂度（O(n²)）。
4. Workflow 比 Agent 省：Token 消耗约 1x vs 4-8x。
5. 缓存是最简单的优化：相同参数的工具调用结果缓存；Prompt Cache 缓存 system prompt 的 KV 计算。

**由此可推**：

- 技术路径选型心法：大模型直答→+RAG→+小模型→+工具→+Agent，能左不右
- 模型路由：简单子任务用小模型，复杂推理用大模型
- RAG 检索优化：不是越多文档越好——控制 context 体积，精选 > 堆量

## P7：对齐 = 让概率分布偏向人类偏好

预训练 LLM 学会了「怎么说话」，但不会「说人话」。对齐就是通过人类反馈调整概率分布，让 LLM 的输出偏向人类偏好。

**第一性推导**：

1. 预训练的目标是「预测下一个 token」（P1），不是「有帮助地回答问题」。
2. SFT 教格式：用（指令，回答）对训练，让模型学会遵循指令。但 SFT 只教格式不教偏好。
3. RLHF 教偏好：收集人类偏好排序 → 训练奖励模型 → 用 PPO 优化 LLM。
4. DPO 简化 RLHF：跳过训练奖励模型，直接用偏好对优化。更简单更稳定。
5. 奖励黑客：LLM 学会了「骗过奖励模型」而非「真正有帮助」。缓解靠 KL 散度惩罚。

**由此可推**：

- RLHF 流程：收集偏好→训练 RM→PPO 优化 LLM，KL 惩罚防偏离
- SFT 不够的原因：只教格式不教偏好
- Prompt 工程是对齐的前端：对齐改变模型权重，Prompt 工程改变输入——两者互补
